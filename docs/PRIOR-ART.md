# PRIOR ART — 我们从别人那里借鉴什么、拒绝什么，以及为什么

- 状态：living（每次评估新插件后更新）
- 读者：本项目维护者与后续 agent（内部设计文档）
- 用途：把「看过哪些实现、为什么采纳/拒绝」记在一处，避免重复调研，也避免我凭印象做决定。

> 这份文档的存在原因：本项目一度是"用户提一个、我做一个"的反应式开发。
> 2026-11-15 的一次反问（"不要我说一个你就搞一个"）之后补上系统性盘点。

## 0. 评估基准（loci 的四条硬不变量，2026-11-15 修正版）

一条设计值不值得抄，先过这四关。违反任何一条的，无论多流行，都不抄。

**这一版是根据独立边界审计改写的。**旧版的措辞比代码更强，而在一次盲评里被逐条打穿：I2 说"字节级不变"，但尾部有日期；I4 说"读永不越界"，但面板枚举全部键。一个说得过满的判据比没有判据更糟 —— 它会让后续每个决定都建立在一个假前提上。所以下面每条都分**断言**与**它什么时候会失效**（后者见 §0.1）。

| # | 不变量 | 断言（代码实际保证的） |
|---|---|---|
| **I1** | 注入闸门 | 只有 `status='verified'` 且未过期、未删除的条目进入提示词。`status` 由 store 重新派生，模型无法通过工具断言它。verified 来自**面板/CLI 的人工操作**，或**用户自己消息里逐字存在且与主张有实质关联的引文**（§2.1 的两问闸门）。 |
| **I2′** | 前缀稳定 | **没有任何写入会重排或改写已有行**；重求值只发生在会话/日边界，绝不在步内。尾部（`as of` 日期、`+N more`、待审提示）允许随写入与 UTC 日期变化。 |
| **I3** | 默认零网络 | 默认配置下不发任何请求。三条可选出网路径：更新检查、HTTP 向量通道、会话结束的抽取（经宿主 `ctx.llm`，非本进程直连）。前两条默认关闭，第三条默认 `off`。 |
| **I4′** | 作用域显式 | **会话内的每一项读取都绑定显式键集**，不使用通配。面板/导出枚举全部键，那是**明确的行政通道**（管理员视图），不是会话读取。作用域键由宿主 `session.header.cwd` 派生；该字段缺失时回落进程 cwd —— 这是已知风险，不是保证。 |

> **旧版 I2 / I4 为什么被替换**：I2 原文"无写入时字节级不变"在 UTC 零点自破（尾部日期），且在 TTL 到期时于会话中途静默改变内容；I4 原文"读永不越界"与 `allScopeKeys()` 的通配枚举矛盾。把它们改宽不是妥协，是把判据改到能被代码验证的精度。

## 0.1 每条不变量什么时候会自动失效

§2.1 给拒绝了的东西写了失效信号，却没给四条不变量写 —— 这是结构性的不对称：**唯一被认真对待的判据，是那个被拒绝的**。补齐如下（判定方式与是否有人会注意到，见审计报告 `reports/2026-11-15-boundary-audit.md`）：

| # | 类别 | 依赖什么 | 失效信号 | 会被注意到吗 |
|---|---|---|---|---|
| I1 | 结构（数据层）/ 语义依赖 | 宿主持续发 `session/event` 让引文缓冲存在 | 缓冲缺失 → 闸门**更严**（fail-safe，全部变候选）；引文门槛或 `autoVerifyCaptured` 默认值改动 → 闸门**更松** | **不会**。所有单测都桩掉验证器，真实函数只在手动 e2e 里跑过 |
| I2′ | 结构（排序）/ 经济性依赖 | provider 的 prefix cache 粒度 | provider 改为按段缓存或取消前缀缓存 → 经济理由消失（安全性理由仍在） | **不会**。仓库里没有任何 cache 命中量；`request_stat` 记的是字节数 |
| I3 | 结构（无直连）/ 计数依赖 | 三个默认布尔值 + 枚举完整性 | 新增经宿主服务的出网（如 `ctx.llm` 的另一处调用）→ grep 门看不见 | **部分**。直接 `fetch` 会挂 CI，宿主中介出网不会 |
| I4′ | 结构（查询）/ 派生依赖 | `session.header.cwd` 存在性 | 会话创建时不带 cwd → 所有此类会话共享宿主进程目录；深目录超过 12 层 → 项目作用域塌成工作区 | **不会**。doctor 不检查作用域身份，无相关测试 |

**这套机制本身是这次审计最有价值的产出**：判据要带失效条件，否则它只是当时当地的偏好，被后人当成真理。任何新增不变量必须同时写它的失效信号。

## 2. 值得借鉴、尚未做（按性价比排序）

### A 级 — 建议下一版做

**A1. 教训的结构化形态（`pattern` / `fix` / `prevents`）**
- 来源：`dsh-project-memory` 的 `save_lesson`
- 问题：loci 的 `procedural` 是自由文本。半年后只看到一句话，看不出"不做会怎样"。
- 落地：schema v3 加可空列 `pattern`/`fix`/`prevents`/`when_condition`；索引行对 procedural 追加 `— prevents: …`（受 `indexLineMaxChars` 约束，默认 120）。
- 风险：索引行变长 → 触发 I2 退化？不会：只在写入时改变一次，之后字节稳定。
- 成本：低（一次迁移 + 一处渲染）。

**A2. 按活跃度淘汰"注入了但从未读"的条目**
- 来源：`dsh-memory-tiers`（六层 + "忘"是流程的一步）、`mem0`（decay 只在检索时生效）、`dsh-fish-memory`（逐条衰减）
- 问题：我们 2.1 装了电表（inject/read 计数），却没有任何策略消费它。
- 落地：`procedural` 类中 `read_count = 0 且 inject_count ≥ N` 者从索引段降级（仍可 `loci_search`），`doctor` 单列一行。
- 风险：误伤"读了但没 `loci_get`（索引行已够用）"的条目 → 用 `read_count + 被引用次数` 双阈值，并先只影响 procedural。
- 成本：中（策略 + 统计口径）。

**A3. 冲突的显式表达（而不只是 supersede）**
- 来源：`memory-eternal` / `supermemory`（`updates`/`extends`/`derives` 边 + `isLatest`）
- 问题：我们现在**只能**"新条目取代旧条目"。真实场景常是"这条改了一半"——例如"回滚窗口 30 分钟"→"回滚窗口 45 分钟，但数据库变更仍是 30 分钟"。
- 落地：`memory_edge` 表已有 `relation` 字段，但**全库只用了一个取值** `supersedes`（`store.js:405`）；补 `conflicts`/`extends` 两种即可复用现有表与索引，无需迁移。`loci_get` 显示"与 m_yyy 冲突/延伸"；注入段不改（仍旧一条），冲突在面板里呈现。
- 风险：低（只增边，不改注入）。
- 成本：中。

**A4. 会话工作状态的"最小接续面"（TaskBridge 的可借部分）**
- 来源：`dsh-project-memory` 的 **TaskBridge**（跨会话任务 + 触碰过的文件，切走再续接）
- 问题：这次会话里我反复手工重建"改过哪些文件、下一步是什么"。loci 现在的 episodic 摘要只存会话文字片段（`capture.js:373-389`），**不记录触碰过的文件**，所以下个会话搜不到"上次改到哪"。
- 落地（最小版，不引入任务面板）：在 episodic 摘要里增加一个结构化字段 `filesTouched`（从本会话工具调用的路径参数提取，去重、限量 30 条），并把它写进摘要正文的一个短列表。episodic **本来就不注入**（`capture.js` 注释：历史不是主张），所以对 **I1/I2 零影响**——只改善"按需检索"。
- 明确不做：任务面板、todo 同步、跨会话绑定（那是 `dsh-project-memory` 的完整产品面）。
- 成本：低（一次提取 + 一处写入）。价值：高（解决"接续要重新问一遍"）。

### B 级 — 有价值，但需要先想清楚

**B1. 报告"记忆缺失"的能力**
- 来源：`dsh-auto-memory` 的 recall funnel（注入了但从没被读）、`mem0` 的 mean tokens/query
- 想法：区分"没有这条记忆"和"有但没召回"。我们已经有 `loci_search` 的 `matchedTotal: null`，但没有"这次会话模型查了什么、没查到什么"的视图。
- 需要想清楚：这属于诊断还是产品？会不会变成又一个用户不看的统计页？

**B2. 导入/导出与跨工具互通**
- 来源：`dsh-cross-memory`（一个库接 DSH/Claude/Codex/Cursor）、Claude Code 的 `@path` 导入
- 现状：我们只做了 auto-memory 与 Claude memory 的**单向导入**。
- 需要想清楚：双向同步会引入冲突解决，而冲突解决正是 A3 还没做的。→ 先做 A3，再谈互通。

**B3. 常驻"画像"层（persona）**
- 来源：`dsh-cross-memory` 的 `persona/human.md`（会话开始注入快照，可锁定防后台改写）
- 想法：把我们散在 `global` scope 的偏好收敛成一个可锁定的小块。
- 顾虑：与索引段功能重叠；且"画像被改写"是用户最敏感的失败。**倾向不做**，除非有真实需求。

### C 级 — 明确拒绝（并记录理由）

| 拒绝项 | 来源 | 理由 |
|---|---|---|
| 写入时自动 cosine 合并（0.9 覆盖） | `dsh-project-memory` | 0.9 相似也可能语义相反（"必须做 X" vs "不许做 X"）。我们保留手动 `merge` + 乐观锁 |
| 空闲"做梦"式整合 | `meow-memory`、Letta `dreaming`、`zzerx` | 后台无监督改写记忆，是"我明明没改它却变了"的来源。**必须有人在场** |
| 自动 scope 晋升（task→project→global） | `dsh-project-memory` 的两/三次晋升 | 违反 **I4**：作用域由使用次数漂移，跨项目泄漏风险不可接受 |
| 每轮全量抽取**作为默认** | `zzerx`、`dsh-cross-memory` 后台抽取 | 每轮一次模型调用 + 每轮一条待审，会让人放弃审阅（2.3 的 digest 就是为此而生）。**这一行说的是"不做默认"，不是"永不"**：本项目自己发货了 `extractMode: 'on'|'turn'`，即按需的逐轮抽取。规则正确读法是"默认关闭，开启时必须明说代价" |
| 把语料正文当注入触发源 | 多家 | 正文可被污染 → 等于让记忆内容决定自己是否入提示词 |
| 外部记忆服务（Hindsight / Honcho / supermemory 云） | `dsh-hindsight`、mnemon providers | 违反 **I3**；且我们权衡过：一次网络往返换来的召回提升不值得把记忆送出去 |
| 常驻大块（resident USER.md/MEMORY.md 全文注入） | `dsh-mnemon` | 提示词成本不可控；索引 + 按需取正文是更省的形状 |
| **代码/文档索引（"读到即索引"）** | `dsh-project-memory`、`basic-memory` | 那是**对仓库内容的 RAG**，不是记忆。加进来会多一条检索通道、一套过期语义和一份"代码的第二份副本"；代码与 AGENTS.md 已是 SSOT，`grep` 比索引更可信 |

### 2.1 拒绝条件注入：理由、适用范围、失效信号

原文只写了一句"违反 I2 / 让记忆内容决定自己是否注入"。那句话**写宽了**，这里把边界说清。

#### 真实的两条理由

| # | 理由 | 性质 |
|---|---|---|
| R-a | 若每步都重算注入集合，系统提示段字节会变 → prefix/KV cache 失效，每次请求多付全量重算 | **经济性**（依赖当前 provider 的缓存实现） |
| R-b | 若"该不该出现"由**已存正文**推断，则被污染的记忆可以把自己拉进提示词 —— 准入权交给了可被污染的数据 | **安全性**（结构性，与实现细节无关） |

#### 适用范围：只对"系统提示段 + 每步求值"成立

R-a 只在**每步求值、且注入点在系统提示段**时成立。会话内只求值一次的方案不违反 I2。
R-b 只在**正文参与判定**时成立。由人工核实过的结构化字段（如 `whenCondition`）参与判定，并不破坏"verified-only"——它只是决定 *verified 里哪些更相关*。

**我们其实已经有一处条件注入**：`recallAssist: 'session-start'`（`src/host/index.js:217-251`）——按首个用户消息检索、每会话一次、以 user message 形式注入、有 `recallAssistBytes` 上限、默认关闭。
所以真正的规则不是"永不做条件注入"，而是下面五条。

#### 可持久的规则（建议按此判定将来任何条件注入提案）

**R1 与 R3 的旧措辞已被代码推翻，这里是修正版。**旧 R1 说"正文永不触发"，但已发货的 `recallAssist` 正是按正文 FTS 命中决定注入 —— 项目一边立规矩一边违反它。旧 R2 说"系统段会话内不变"，而待审计数在渲染缓存键里，这正是**故意**让它随写入变化。规矩要与实现一致，否则它只是一句愿望。

1. **R1 正文不参与注入选取**（限定为索引段）：**索引段**的选取不读正文 —— SELECT 里没有 body，只有 id/kind/date/title。`recallAssist` 是**明确的例外**：按正文检索、每会话一次、注入为 user message、有字节上限、默认关闭。例外不算违规，前提是它被写下来且被单独约束（R3′/R4/R5）。将来任何按正文选取注入集的提案，仍然按拒绝处理。
2. **R2 提前一个边界，而非禁止改变**：条件求值不得发生在**步内**；允许发生在会话/日边界。已发货的待审计数是**边界例外**：它随写入变化，代价是前缀可能失效，这是知情选择（§2.1 R-a 记为未测量的经济赌注），不是疏忽。
3. **R3 只允许在会话边界求值**，且输入必须是可复现快照。**当前 `recallAssist` 只满足前半句**：它读实时库并用墙钟做时效加权，同一库重放可能得到不同排序。所以 R3 目前是一条**待实现**的规则，不是已满足的事实。
4. **R4 可解释**：每条被条件选中的条目，必须在面板或审计里回答"为什么这次出现"。**索引段满足；`recallAssist` 不满足** —— 它不写 `request_stat`、不写 `memory_usage`，审计行里没有 id 也没有 session。这是待补的缺口。
5. **R5 可选且有界**：默认关闭、有字节上限、可随时关掉。**已满足**（`recallAssist` 默认 `off`，`recallAssistBytes` 默认 512、上限 2048，每会话一次）。

> 修正原则：一条规则如果代码违反它、且没有任何测试或检查发现，那么真正生效的不是规则，是代码。把规则改成代码实际的样子（并标明待补的部分），比保留一句漂亮话有用。

#### 什么时候这条拒绝会自动失效（失效信号）

- provider 改为**按段落分别缓存**，或不再对 system prefix 做缓存 → R-a 的经济理由消失（R-b 仍在）；
- 条件改由**人工显式勾选**（不是模型推断）→ R-b 弱化为"人做的决定"，仅剩可解释性要求；
- 我们真出现"条目数远超预算、且相关性差异巨大"的实测数据 → 静态索引的代价超过条件注入的代价。

在此之前，维持"存条件、不判条件"。这不是永久真理，是当前四条不变量下的最优解。

## 3. 口径变更记录（为什么不一致，而不是假装一致）
这份文档的第一版与我会话里的口头建议**不一致**，此处记录差异与裁决：

| 我先前口头说的 | 文档最初的处置 | 现在的裁决 |
|---|---|---|
| 触发式注入"值得借鉴" | 直接进了 C 级拒绝 | **改判为部分采纳**：`when_condition` 存而不判（A1）。口头说"值得借鉴"时我只想到"条件命中更准"，没想到它会破坏 I2 与"正文不能决定自己是否注入"这条安全线 |
| TaskBridge"值得借鉴" | **漏写**（文档里根本没有） | **补为 A4**：只借"会话工作状态的最小接续面"（episodic 里记 `filesTouched`），不做任务面板 |
| 读到即索引"值得借鉴" | **漏写** | **补为 C 级拒绝**：它是 RAG，不是记忆；与 loci 的产品边界冲突 |

教训：口头列"值得借鉴"很容易把三个不同性质的层次（结构化字段 / 工作状态 / 检索架构）混成一类。
**判据必须写在前面（本文 §0 的四条不变量），否则"值得"只是感觉。**

## 4. 一条元教训（比上面任何功能都重要）

看过的 8 个 DSH 记忆插件里，**只有 2 个把"未核实不进提示词"做成代码级不变量**（loci 与 auto-memory），其余的都靠 prompt 里的劝说或干脆没有这层。
也就是说：这个品类里"功能更多"几乎总是意味着"闸门更松"。**我们不追功能数量，追的是"它出错时最坏能坏到什么程度"。**
