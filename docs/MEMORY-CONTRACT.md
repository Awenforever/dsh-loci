# 记与忆的契约

> 两个工具、三个写入者、一条反馈回路。本文定义模型能表达什么、系统替它回答什么，以及它如何被纠正。
>
> 起因（2026-11-17）：一条只在"改位置切换图标"时才相关的规则被注入了 **397 次**。根因不是排序不公，
> 而是 `loci_write` **根本没有表达"何时适用"的参数**——`importance` 有列、有排序、参与决定 core，
> 却从来没有入口，全库 29 条恒为默认值 3。**系统缺的不是"让模型判断"的能力，是"让判断有地方可写"。**

## 0. 一条判据

> **不要让模型填它能查到的，也不要让系统替模型做只有它能做的判断。**

按这条线切开：

| 问题 | 谁回答 | 为什么 |
|---|---|---|
| 这条对用户多重要 | 模型 | 只有它在对话现场 |
| 这条谈论的对象是否每个任务都出现 | 模型 | 只有它知道当前任务在做什么 |
| 这条是否与其他记忆雷同 | **系统** | 模型看不到全库，让它猜就是碰运气 |
| 这条是否推翻了一条旧记忆 | **系统提议 + 模型确认** | 系统能检索到相似条目，模型判断是不是同一件事 |
| 这条写了之后有没有生效 | **系统** | 可计算：是否被注入、是否被更新、是否与别的矛盾 |

## 1. `applies` —— 何时适用

```ts
applies: 'always' | 'topic'
```

**判据是一句话**：这条规则谈论的**对象**，是否出现在每一个任务里？

- `always`：谈论的是工作方式本身。`AGENTS.md 只留指针`、`最终验收必须亲自截图`、`查端口用 netstat + PID`
- `topic`：谈论的是某个东西。`网格视图卡片只显示流量偏差`、`位置切换图标不要用左右箭头`

这不是"有没有硬约束"的区分——`both` 组（关于单个 UI 元素的硬约束）全部是 `topic`，因为那个元素
只在相关任务里出现。真实库里按措辞粗分：standing-only 10 · subject-only 10 · **both 5** · neither 1，
那 5 条 `both` 正是最容易判错的地方。

**判据的推论**：`always` 应当**罕见**。绝大多数记忆是 `topic`。如果一个库大部分是 `always`，
说明判据没被遵守——core 会重新被塞满，这个字段就白加了。

**默认值 `topic`**：宁可走检索，不要无条件注入。默认 `always` 会把今天的 bug 固化成默认行为。

### 值域是两值还是三值，由实验决定

`project`（"这个项目的所有任务都要遵守"）是个诱人的中间态。但在有证据前不实现——三个值意味着
core 要决定"当前项目"是哪个，而 scope 已经有这个概念，两个字段表达同一件事会分裂。

**判定方法见 §6。**

## 2. `importance` —— 给它真正的入口，但别假装精确

`importance INTEGER DEFAULT 3` 已经存在，参与 `selectCore` 排序，但**没有任何调用方传值**。
要么给它入口，要么删掉它——留着一个永远等于 3 的排序键，等于假装有区分度。

### 第一版的想法是错的

我最初写的锚点是"违背它的后果有多严重"。**那个量在写入时没人知道**：

- 模型在写入当下不知道后果
- 人知道但不会逐条填
- 预先写死的判据表一定失效——`importance` 全是 3 就是证据

所以入口保留，但语义改成：**模型的主观判断，允许错，日后由系统修正**。

```
5 = 你看到它没被遵守会意外
3 = 有用
1 = 写给自己看的备忘
```

### 修正机制：现在做不了，原因要先写清楚

计划是用 `update` / `forget` 的次数当修正信号。查了真实库：

| 信号 | 现状 | 可用性 |
|---|---|---|
| `revision > 1` | 5 条 —— **全部是我迁移 `applies` 造成的** | 暂时被污染 |
| 曾被打 `deleted` | 6 条 —— **全部是清理注入回声** | 暂时被污染 |
| `read_count > 0` | **0 / 39** | **永远不可用** |

`read_count` 恒为 0 不是缺陷：标题自包含时模型不需要展开（见 `docs/REAL-TRAFFIC.md`）。
任何依赖它的公式都会"除以零，然后判定每条记忆都完美"。

**结论：自动修正推迟**，先把信号采集对：

1. `revision` 计数要能区分**内容修正**与**元数据变更**（改 `applies` 不算记忆变不准）；
2. 用户显式强调（"记住这条"）要成为独立信号，而不是靠模型猜；
3. 不实现任何依赖 `read_count` 的公式。

**这是本文件里唯一一条"已知该做但数据还不存在"的项**，写在这里以免将来被当成遗漏。

## 2.1 顺带修正：条件必须和标题一起出现

`whenCondition` 在 v3 就有列，存了、`loci_get` 能取，但**注入行从来不显示它**。

一条条件性事实被渲染成无条件标题，比不注入更糟——模型会从一个它看不见的前提上推理。
现在渲染为 `· when: <条件>`（截 60 字符）。

这条是用户提出的："VM 是运行在 invictus 上的，所以只要 invictus 可达，VM 就可达，
**不是单纯的 always 就能判定的**"。它同时说明了 `applies` 与 `whenCondition` 是两个维度：

- `applies` 决定**要不要每轮展示**（展示策略）
- `whenCondition` 说明**这条在什么条件下为真**（语义前提）

把它硬标成 `always` 会让模型当成无条件真理。

## 3. core 与 slice 的分工重建

```
core  = applies='always' 的条目，按 importance / μ 排序
slice = 其余条目，按与当前问题的相关性检索
```

**核心可能为空，这是正确的**。一个新建的库没有 `always` 条目时，core 就该是空的——
正文说明"ages in μ"那行仍然保留，因为 slice 会用到它。

**兜底**：core 为空时，**不**从 topic 里捞几条来填。填空会让"core 是 always"这个契约失效，
而失效的方式很隐蔽——面板显示有内容，阅读者以为那些都是 always。

### 3.1 字节上限不是主约束

原来的 `CORE_BUDGET_BYTES = 500`，来历是（git `b561bfc`）：

> hard 500 B cap（a first version also admitted every semantic entry ordered by recency, which put six
> pieces of filler under the heading 'Always applies'）

**它是为了"防填充物"设的上限，不是测出来的容量。** 当时真正的问题是"什么该进 core"，
却用"让你装不下"绕开了。`applies` 正面回答那个问题之后，这个上限就失去了原来的职责。

代价是可见的：4 条 standing 需要 558 B，于是**字节在暗中决定只显示 3 条**，
而 `CORE_MAX_ENTRIES`（"每轮最多几条"才是设计意图）被一个没测过的数字推翻。

现在：**字节上限退为安全阀（1500）**，只防单条异常长；`CORE_MAX_ENTRIES` 做主约束。

### 3.2 但条目数（6）也还没有依据

我一度说"经验上 5–9 条"，那是人类短期记忆的研究，与 agent 每轮需要多少条规则无关——
**拍脑袋，该撤回**。

去统计了真实长会话（`scripts/diag/standing-evidence.mjs`），得到"≥90% 渲染中出现"的条目数：

```
median 1 · max 1
```

**但这个数字不能当依据**，它有一个循环论证：统计的是"过去哪些条目反复出现"，
而过去的 core 是**旧代码**决定的（所有 `kind='rule'` 都塞进去）。**不能用坏系统的输出去论证好系统该多大。**

所以：6 是**待校准的默认值**，不是测量值。校准方法写在 §6。

## 4. 三个写入者必须对齐

| 写入者 | 触发 | `applies` 由谁定 | 状态 |
|---|---|---|---|
| `loci_write` | 模型主动 | 模型，在参数里 | ✅ |
| curator | session-end | 模型，在 curation prompt 里 | ✅ |
| 规则提取器 | 每轮 prefilter | **不判，默认 topic** | ✅ 有意为之 |

前两个是模型判断，第三个不是——这一条要写清楚理由：

`extractor` 的产物 `trustSource` 是 **`summary`**，含义是"提议，不是证词"。它用模式匹配从用户消息里
捞出可能的偏好，**没有做语义判断的能力，也没有上下文**去回答"这条谈论的对象是否每个任务都出现"。
让它猜一个 `always`，就是把一个它答不了的问题变成一条永久的错误。

所以它**不传** `applies`，落库即是 `topic`。这类记忆本来也要走 quote gate 才有资格变 verified，
升级为 `always` 应当是后续的显式动作（人 `pin`，或模型在 `loci_write` 里改），不是提取器的猜测。

对齐的检查点只有一处：`store.write → prepareForStorage`。所有写入者都经过它，
所以字段的保留与校验在那里做，不必每个调用点各写一遍。

## 5. 反馈回路（A 方案：搭便车）

**约束**：模型不会主动查询记忆系统的健康状况。它只在需要时调工具。所以反馈必须长在它本来就会做的
动作上——**写入**。

`loci_write` 的返回值除了"保存成功"，还要带：

1. **相似条目**——系统检索出来的，不是模型猜的。"你写的这条与 `m_xxx`（相似度 0.82）接近，
   如果说的是同一件事，用 `op:'update'` 或 `op:'merge'`。"
2. **未生效的近期写入**——"你最近写的 5 条里有 3 条从未被注入过。可能是 scope 标错了。"
3. **待审队列**——"还有 N 条记忆在等审核，它们不会进入提示词。"
4. **冲突**——"这条与 `m_yyy` 冲突，两条都说要做 X 但做法不同。"

**为什么是这四条**：它们都是系统**能算**的，而且都指向模型能当场纠正的动作。
不包含"这条有没有用"——那需要观测任务结果，系统看不到，写进去就是编造。

## 6. `applies` 值域的判定实验

不靠讨论定，靠数据定。方法是**观察误判的形态**：

1. 上线两值版本，模型自行判断；
2. 收集两类误判：
   - 标了 `always`、但**连续 N 轮没有任何任务与它相关** → 太宽
   - 标了 `topic`、但**反复在无关任务里被检索到并需要** → 太窄
3. 如果"太窄"的案例里，相当大的比例属于同一个模式（"这个项目的所有任务"），
   那么 `project` 这个中间值有依据；否则两值够了。

**先实现两值**，因为它可以被证伪。三值在没证据时实现，就是给一个还没确认的问题造答案。

## 7. 这套契约失败的形态

写下来，以便将来发现时认得：

| 失败 | 症状 | 原因 |
|---|---|---|
| 所有条目都是 `always` | core 又满了 | 判据没传达给模型，或工具描述写得像"越重要越该 always" |
| 所有条目都是 `topic` | core 永远空 | 模型不知道 `always` 长什么样，需要例子 |
| importance 全是一个值 | 排序退化成 μ | 锚点不够具体，或默认值太舒服 |
| 反馈被忽略 | 返回值带了但模型不看 | 反馈太长；它不是指令，是信息 |
| `always` 判对但没用 | core 里的东西确实每轮都在 | 正常——这才是要的效果，不是 bug |

## 8. 不做的事

- **不做自动压缩**。判据在 `docs/REAL-TRAFFIC.md` §2.2：`read_count` 全 0 是标题自包含的正常状态，
  按"未展开"压缩会砍掉全部核心规则。
- **不让模型填相似度**。见 §0。
- **不给 core 设"最少条数"**。见 §3。
