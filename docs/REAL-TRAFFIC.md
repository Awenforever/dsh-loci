# 真实流量分析：一个会话教会我们的事

> 数据取自 `session-4c45fb3c`（DSH-USTC-Quota）48 小时窗口，一台真实在用的机器，不是夹具。
> 目的：用真实分布检验 R18 / 压缩动力学 / R27 三个待办问题的**前提**，而不是先写实现再找依据。
>
> **这些数字会变。** 该会话仍在运行，第二次采样时总注入已从 3009 长到 3015、单条最高从 397 长到 399。
> 下面记录的是某一时刻的快照；趋势比绝对值重要，复现命令见 §6。

## 2. 这否定了三个预设

### 2.1 R27「忆多少」——预算不是瓶颈，方向错了

我原本打算扫 `SLICE_BUDGET_BYTES`，找出"最优预算"。真实数据说这条路没有意义：

```
上限：CORE_BUDGET_BYTES 500 + SLICE_BUDGET_BYTES 1200 = 1700 B
实测：p50 678 B · max 792 B
```

**用了不到一半**，而且 max 也只到 792。提高 1200 不会带回更多内容——`selectSlice` 的候选池里就没有那么多相关的。

> **结论：R27 的真正对象是候选池，不是预算上限。** 继续调预算是在优化一个没有约束力的参数。
> 该测的是「提高候选召回率会不会改善答案」，而 `loci_answer_eval` 现在正好能测。

### 2.2 压缩动力学——不能依赖 `read_count`

我原本设想的压缩判据之一是"长期未被使用就压缩"。真实数据：

```
被注入后被打开过：0 / 25
```

**一条都没有**。如果按 `read_count = 0` 压缩，会把**全部 25 条核心规则**砍掉——包括那 397 次注入的"位置切换图标"规则，它显然每轮都需要。

原因不是用户不用，而是**标题自包含**：

```
「只读模式与演示模式必须自动互斥」
「AGENTS.md 只留指针，不写案例细节或事故经过」
```

标题就是完整规则，模型不需要 `loci_get` 就能照做。`read_count = 0` 在这是**正常工作状态**，不是弃用信号。

> **结论：压缩判据必须来自 `importance` / `pinned` / "是否每轮都需要"，不能来自 `read_count`。**
> 把"未展开"当"未使用"会砍掉整个产品最有价值的部分。

### 2.3 注入即刷新时钟——循环存在，但性质要分清

代码里 `recordInjection` 会 `mu_touched = 当前 μ`，而 `selectCore` 按 `mu_touched DESC` 排序：

```
注入 → 变最新 → 下次优先选中 → 再注入 → 再变最新
```

这确实是个自我强化的循环。**但**：如果这些条目每轮都真的需要，常驻是正确行为，不是 bug。真实数据里 25 条参与轮转（不是固定 8 条），说明流动性存在。

真正的风险在别处：**新条目要挤进那 500 B 的 core，必须比现存的 8 条"更新"**。而现存 8 条每次注入都刷新到当前 μ，所以新条目永远比不过它们，只能进 slice。

> **结论：循环在 core 段是设计使然；它的代价是「新规则进不了 core」。** 这需要在压缩动力学里一并考虑，
> 解决方案不是取消 touch，而是给 core 一个**轮换/冷却**机制。

## 3. 对 R18 的指导

真实流量解释了为什么 `loci_answer_eval` 的 with/without 设计是对的：

- 注入的标题确实承载了信息（25 条里没有一条需要展开）
- 所以"带记忆块 vs 不带"就是这个产品真实的增益路径

但也提了个醒：**控制题 invented 2/2** 说明模型会编。在真实流量下这意味着什么，目前**不知道**——因为没法观测"模型是否编造了一条记忆里没有的规则"。这是 `loci_answer_eval` 之外、真实任务里的一个未知。

## 4. curation 在本会话的表现

```
启动 50 · 运行 10 · 写入 0 条
原因：nothing to read 24 · no candidate sentence 11 · (none) 10 · reply is not JSON 1 · reply has no keep array 1
```

`(none)` 10 次是审计本身的缺陷：`reason` 由调用方控制，缺了就记空（已记为 R21）。

## 5. `remove_bundle` 非原子

本会话的流量数据与它无关。但同一天在本会话里验证过：**先说让 pnpm 能解析**
（`pnpm install --lockfile-only` 把违规版本写进 exclude），**再** `remove_bundle` / `install_bundle`，
正规路径全程走通（5.1.4，65 文件逐字节一致）。前几轮失败都是顺序错了。

```bash
node scripts/diag/session-traffic.mjs 4c45fb3c --hours=48   # 一个会话对记忆系统做了什么

```

两个脚本都只读。数字来自 `request_stat`、`memory_usage` 与 `audit.jsonl`，不是估算。
