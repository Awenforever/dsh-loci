# 记忆单位与弹性记忆空间

> 回答一个问题：记忆空间会无限增长吗？应当让早期记忆随记忆增长而压缩吗？
>
> 本文只定义模型与判据，不含实现。实现前先冻结这里的概念，否则"早期"三个字会在代码里变成三种意思。

## 1. 为什么不能用墙钟时间

`2026-11-16 20:00` 到 `2026-11-17 04:00` 是 8 小时，但对 dsh-loci 而言可能什么都没发生：用户睡了，DSH 没有在一次工作里流过任何时间。

用墙钟定义一个"早期"，会导致：

- 一夜之后，**所有**记忆同龄化地变老 8 小时，尽管其间没有任何召回、没有任何新记忆；
- 而一次长 session 里连续 200 轮，实际发生了大量交互，墙钟可能只过了 2 小时。

**时间的流逝应当由"发生过多少记忆事件"来计量，而不是由地球自转来计量。**

## 2. 记忆单位（MU, memory unit）

一个 MU 只在**活跃**状态下累积。定义：

```
MU 的增量 = LOG(w_add × 新增记忆量 + w_use × 召回活动量 + 1)
```

取对数而不是线性，是为了让"再发生一点"的边际寿命消耗递减——这是下面 §3 对数曲线的来源，也是"塞入大量记忆不会加速旧记忆死亡"这一性质的数学基础。

其中：

| 量 | 含义 | 为什么必须有 |
|---|---|---|
| **新增记忆量** `add` | 本轮真正落库且 `verified` 的条目数（按内容字节归一到 0–1） | 记忆膨胀率。塞进一堆文档，是记忆生长的主因 |
| **召回活动量** `use` | 本轮被注入的条目数 + 被 `loci_get` 回查的次数，归一到 0–1 | 活跃时间。只有被用到，时间才真的流过 |

**关键性质：`add = use = 0` 时 MU 不增长。** 用户睡觉、DSH 闲置、只是打开界面看了一眼——都不消耗任何记忆的寿命。

这就是"记忆单位"相对墙钟的全部价值：它是**因果时间**，不是天文时间。

### 归一化

`add` 和 `use` 各自除以一个**滑动窗口内的典型值**（例如最近 50 个 MU 的均值），使：

- 一次接手新项目、读 50 篇文档 = `add` 很大、`use` 中等 → MU 快速推进；
- 一次深夜长聊、没有新知识 = `add` 很小、`use` 大 → MU 稳步推进；
- 两者都为零 = 冻结。

## 3. 坐标轴：0 是平衡点

```
遗忘 ←—— −  —— 0 ——  +  ——→ 修剪
   压缩/丢细节        去枝末/归纳/碎片整理
```

每条记忆在这根轴上有一个位置 `p`，单位是 MU：

- `p = 0`：刚刚平衡——它是"当下"的记忆；
- `p > 0`（右侧）：**比当下更新，正在被修剪**。新记忆需要在被真正使用前先经过整理：去重、合并、丢弃碎枝末节、把若干条归纳成一条；
- `p < 0`（左侧）：**比当下更旧，正在被遗忘**——但它不是删除，是**压缩**：保留结论，丢掉细节。

### 为什么右侧要存在

这一点容易被跳过，但它解决的是真实问题：**一次性灌入大量新记忆时，新记忆自己也是噪音**。

接手一个新项目，读 50 篇文档，其中 40 篇是一次性的、5 篇是重复的、5 篇才是长期的。如果只在"旧记忆侧"做压缩，那么新记忆会原封不动地占据空间，且**以新近度优势挤掉旧记忆**——这正是当前实现的缺陷（`ORDER BY updated_at`）。

所以右侧的工作是：**新记忆在被信任之前，先被整理一遍**。这是"碎片整理 + 归纳"，不是遗忘。

### 两侧都是对数曲线

从 0 向左走，压缩强度大致按 log 增长；从 0 向右走，修剪强度同理。这与实测一致：最开始的几步压缩收益最大（去掉冗余措辞、合并重复），越往后收益越递减（该丢的已经丢了）。

**对数形状是刻意的，它带来两个必需性质：**

1. **短时间内塞入大量记忆，不会让旧记忆更快消失。** 因为 MU 的推进速度由 `add` 归一化后决定，对数曲线使"再推一步"的边际压缩量越来越小；峰值压缩率被压住。
2. **对话轮次很多但记忆没怎么增长时，旧记忆不会持续被侵蚀。** 因为 `add ≈ 0` 时 MU 增量主要由 `use` 决定，而 `use` 的增长同样被对数压住；且**没有新增就没有压缩压力**——压缩的驱动是"空间紧张"，而空间不是固定值。

## 4. 记忆空间是流体，不是容器

这是整个模型的核心，也是最容易被实现成错的地方。

**不要**把记忆空间想成一个固定容量的桶，满了就挤掉最旧的。那种模型必然导致：塞入 50 篇文档 → 旧记忆被挤掉。这正是你不想要的。

正确的模型：**记忆空间是一根有弹性的带子。**

```
一次吞下蓝鲸后：
[旧记忆 —— 保持不动 ——] [================ 新记忆，鼓起来 ================]
                                    ↑ 消化区（p > 0，慢速修剪，不急于腾地方）

细水长流时：
[======== 均匀分布，长而平 ========]
```

- **它可以拉得很长**：没有空间压力时，新旧记忆共存，谁也不压缩谁；
- **中间可以很鼓**：一次涌入大量记忆时，新记忆先进入"消化区"，在若干 MU 内被慢慢归纳、去重、合并，而**旧记忆不动**；
- 只有当新增记忆的总量**真正超过带子的承载能力**时，压缩才开始向左侧传导——而且按对数衰减。

换句话说：**压缩的触发条件是"记忆膨胀超过了弹性余量"，不是"时间过去了"。**

## 5. 由此得到的判据（可观测、可测试）

| 判据 | 含义 | 怎么验 |
|---|---|---|
| **冻结性** | `add = 0 且 use = 0` 时，任何记忆的位置 `p` 不变 | 空闲 10 分钟后 `p` 完全相同 |
| **抗淹没** | 一次灌入 N 条新记忆，旧记忆的 `p` 变化 ≤ ε | 灌 50 条，检查旧条目压缩级不变 |
| **不因话痨而遗忘** | 50 轮无新增，旧记忆 `p` 变化 ≤ ε | 长对话测试 |
| **消化区收敛** | 新记忆在 K 个 MU 内被整理（重复合并、碎枝丢弃），随后转入常规 | 检查消化期前后条目数与字节 |
| **弹性** | 总量上升时，单条压缩级上升慢于线性 | 对照线性基线 |

**这些判据里没有一条用到墙钟。** 这是这个设计成立与否的试金石。

## 6. 与当前实现的距离（诚实清单）

现在已经有的：

- `memory_usage`（`inject_count`、`read_count`、`last_injected_at`、`last_read_at`）→ 是 `use` 的原料；
- `memory.importance`、`pinned`、`kind` → 压缩时的保护等级；
- `memory_edge`、去重（`possibleDuplicates`）→ 是"归纳/合并"的原料；
- `memory_head` / `revision` → 压缩可以写成**新 revision**，历史不丢；
- 记忆单位需要的计数器**不必新建**，可以从 `request_stat` + `write` 事件聚合。

还缺的：

1. **MU 计数器本身**（需要持久化，且要能解释"为什么涨了"）；
2. **位置 `p` 的存储**（每条记忆一个 `mu_position`）；
3. **压缩执行器**：把一条记忆压成更短的形式（这一步要模型，属"记"的职责）；
4. **弹性余量的定义**（多大算"鼓"，即压缩开始传导的阈值）——**这个必须先测量再定，不能拍**。

第 4 条是本设计里唯一还没有数字的地方，而项目已经吃过一次"预算是拍的"的亏（`SLICE_BUDGET_BYTES = 1200` 至今没有收益测量）。**这一条留到有测量手段之后再定。**

## 7. 一个必须写下来的反对意见

有人在读到这里时应该会问：**为什么不干脆全部保留，永不删除？**

答案是成本确实存在，但不是磁盘——磁盘很便宜。成本在**召回**：

- 注入切片只有 1200 字节，条目越多，单位字节里有用的比例越低（实测：600 条时精确率 7.5%）；
- 检索的候选窗口是有限的（`LIMIT 600`），条目越多，真正相关的那条越容易被挤出窗口；
- 整理本身**提高**可用性：把三条重复的合成一条，召回时一次命中就等于原来三次。

所以压缩不是"因为放不下才丢"，而是**"因为不整理会变差才整理"**。这也是为什么右侧（修剪新记忆）和左侧（压缩旧记忆）是同一个动作的两个方向，而不是两个阶段。
