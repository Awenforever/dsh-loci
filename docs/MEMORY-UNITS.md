# 记忆单位与弹性记忆空间

> 回答一个问题：记忆空间会无限增长吗？应当让早期记忆随记忆增长而压缩吗？
>
> 本文只定义模型与判据，不含实现。实现前先冻结这里的概念，否则"早期"三个字会在代码里变成三种意思。

## 0. 第一原则：在这个空间里，记忆单位是唯一的时间

这不是"尽量别用墙钟"，而是一条本体论约定：

> **在 dsh-loci 的空间里，没有"时间"这个独立概念。记忆单位的流动就是一切行为的标尺。**
>
> 说"流动"，指的是 **MU 发生了变化**；说"更早/更旧/过期/该忘了"，指的只能是 **`p` 更靠左**。

由此可推出三条硬约束，任何一条被违反，都是在系统里偷偷引入了第二个时间：

| 约束 | 含义 | 违反的例子 |
|---|---|---|
| **C1 无墙钟遗忘** | 记忆不能因为地球自转而失效 | `working` 7 天过期、`candidate` 30 天关闭 |
| **C2 无墙钟排序** | "新旧"只能用 MU 距离表达 | `ORDER BY updated_at`、`exp(-age/30d)` |
| **C3 无墙钟呈现** | 给模型看的年龄必须是 MU，不是日历 | 提示词里渲染 `as of 2026-11-16` |

三条都不是抽象洁癖——墙钟在这三处各自会产生一个具体的错误结论：

- **C1**：一份两个月没被召回、但下季度就要用的口径会被删掉，因为"它旧了"；而它其实只是**没被用**。
- **C2**：一条昨天刚写、从未被使用的记录，会排在一条天天在用、写于去年的规则前面，因为"它新"。
- **C3**：模型看到 `as of 2026-11-16` 会开始按人类日历推理"这已经过时了"，而我们真正想告诉它的是"这条记忆离工作集有多远"。

**当前的实现同时违反了这三条**（见 §5 的诚实清单）。所以引入记忆单位不是增加一个功能，而是**撤掉一个已经在运行的错误行为**。

## 1. 为什么不能用墙钟时间

`2026-11-16 20:00` 到 `2026-11-17 04:00` 是 8 小时，但对 dsh-loci 而言可能什么都没发生：用户睡了，DSH 没有在一次工作里流过任何时间。

用墙钟定义一个"早期"，会导致：

- 一夜之后，**所有**记忆同龄化地变老 8 小时，尽管其间没有任何召回、没有任何新记忆；
- 而一次长 session 里连续 200 轮，实际发生了大量交互，墙钟可能只过了 2 小时。

**时间的流逝应当由"发生过多少记忆事件"来计量，而不是由地球自转来计量。**

## 2. 记忆单位（MU, memory unit）

一个 MU 只在**活跃**状态下累积。定义：

```
MU 的增量 = LOG(w_add × 新增记忆量 + w_use × 召回活动量 + 1)
```

取对数而不是线性，是为了让"再发生一点"的边际寿命消耗递减——这是下面 §3 对数曲线的来源，也是"塞入大量记忆不会加速旧记忆死亡"这一性质的数学基础。

其中：

| 量 | 含义 | 为什么必须有 |
|---|---|---|
| **新增记忆量** `add` | 本轮真正落库且 `verified` 的条目数（按内容字节归一到 0–1） | 记忆膨胀率。塞进一堆文档，是记忆生长的主因 |
| **召回活动量** `use` | 本轮被注入的条目数 + 被 `loci_get` 回查的次数，归一到 0–1 | 活跃时间。只有被用到，时间才真的流过 |

**关键性质：`add = use = 0` 时 MU 不增长。** 用户睡觉、DSH 闲置、只是打开界面看了一眼——都不消耗任何记忆的寿命。

这就是"记忆单位"相对墙钟的全部价值：它是**因果时间**，不是天文时间。

### 归一化

`add` 和 `use` 各自除以一个**滑动窗口内的典型值**（例如最近 50 个 MU 的均值），使：

- 一次接手新项目、读 50 篇文档 = `add` 很大、`use` 中等 → MU 快速推进；
- 一次深夜长聊、没有新知识 = `add` 很小、`use` 大 → MU 稳步推进；
- 两者都为零 = 冻结。

## 3. 坐标轴：0 是栖息地，最右端是入口

```
遗忘 ←—— −  ——← 0 ←—— 修剪 ——← + ←—— 新记忆在这里落下
   压缩/丢细节              去枝末/归纳      （log 尾部，边际）
```

**所有箭头都朝左，那是时间流动的方向。** 一条记忆的全部生命就是沿着这根轴向左走，外加被召回时向右的逆行。

每条记忆有一个位置 `p`，单位是 MU。三段的含义各不相同：

| 区域 | 状态 | 发生了什么 |
|---|---|---|
| **最右端 `p ≈ +R`** | **入口** | 新记忆在此落下。此时处于对数曲线的**尾部/边际**，变化极慢——这正是"吞下蓝鲸也不慌"的来源 |
| **`+` 区（0 与入口之间）** | **消化区** | 向左滑行，越靠近 0 **修剪越深**：去重、合并、丢碎枝末节、若干条归纳成一条 |
| **`p = 0`** | **栖息地** | 消化完成、结构干净的记忆停留之处。**绝大多数有用的记忆应当在 0 附近** |
| **`−` 区（0 之左）** | **压缩区** | 刚过 0 时压缩**很频繁**（细节丢得快，因为冗余最多）；越往左压缩越少——已经无可再压，只剩**与同质记忆慢慢合并** |
| **最左端** | **遗忘** | 合并到最后，成为可遗忘之物 |

注意 0 不是一个"时间戳"，而是**平衡点**：0 附近是唯一一个"没有损失"的位置——右侧还在被整理，左侧已经开始丢细节。

### 3.1 动力学：时间推左，召回拉右

```
       ←—— 无条件向左（每个 MU）  ——←
    ───────────────────────────────●───────
       ——→ 召回一次，向右逆行 ←——
```

- **向左是无条件的。** 不论召回多少次，每个 MU 都会把每条记忆往左推一点。用你原话说：时间也许可以逆转，但不可抵抗。它保证了**终止性**——没有任何记忆能被永久钉在原地。
- **召回是向右的逆行**，幅度同样按对数：**0 两侧是 log 头部（大幅），离 0 越远越接近尾部（微幅）**。

这条曲线形状不是装饰，它一次给出三个必需性质：

1. **稍微老化的记忆，一次召回就能救回。** 0 附近逆幅大，一点使用就把它推回 0 右。
2. **老化太远的记忆，要救就贵了。** 尾部逆幅微，需要反复召回才移动一点——所以"用过一次"和"一直在用"的差距不会被一次偶然使用抹平。
3. **召回会触发重新整理。** 被推向右的记忆若要回到 0，必须**再次穿过消化区**。于是"经常被用"的记忆会被反复归纳，而不是被固化成一个不再变动的旧条目。

### 3.2 为什么大多数有用的记忆会停在 0 附近

这不是设定，是上面两条力的**稳态结果**：

- 一条记忆若被召回得足够频繁，右行与左行在 0 附近抵消，它**围绕 0 振荡**；
- 召回频率低于某阈值，左行胜出，它缓慢滑进压缩区，细节渐失；
- 从未被召回的，一路向左，最终合并、遗忘；
- 新来的在右端排队消化。

于是整条轴形成一个**三档分布**：右端是待消化的一小撮，0 附近是活跃工作集，左端是正在淡出的陈旧层。这正是"绝大多数有用记忆落在 0 附近"的机制，而**没用一条规则去指名谁该留下**。

### 3.3 与"弹性带"的关系，以及我上一版写错的地方

我上一版说"压缩的触发条件是记忆膨胀超过弹性余量，不是时间过去了"。**这在你的模型下是错的**：左行是无条件的，时间本身就会推进它。

修正后的关系是：**弹性带说的是"入口深度 `R` 与消化时间"，不是"压缩的触发条件"**。

一次灌入 50 条文档 → 它们全部落在右端（对数尾部，移动极慢）→ 在消化区里被反复归纳 → **旧记忆根本不在这一段，所以完全不受冲击**。这就是"吞下蓝鲸不挤掉旧记忆"的真正机制：**不是空间有弹性，而是新记忆的着陆点在远处**。

顺带这也回答了一个留给实现的问题：**`R` 该多大**。R 大 → 消化慢、缓冲厚；R 小 → 新记忆很快到达 0，冲击工作集。这是**必须测量的参数**，与下面的弹性余量同属"不许拍"的一类。


## 4. 由此得到的判据（可观测、可测试）

| 判据 | 含义 | 怎么验 |
|---|---|---|
| **冻结性** | `add = 0 且 use = 0` 时，任何记忆的 `p` 不变 | MU 不推进时逐条比对 `p`，结果必须完全相同 |
| **入口缓冲区** | 一次灌入 N 条新记忆，**已处于 0 或 − 区的条目 `p` 变化 ≤ ε** | 灌 50 条，检查既有条目位置不动 |
| **时间只向前** | 任意记忆 `p` 的长期趋势单调不增，无论召回多频繁 | 高召回条目也只围绕 0 振荡，不得持续右移 |
| **无深渊** | 任何一条被持续召回的条目都不会落到 `p < p_floor` | 久置后恢复召回的条目能回到 0 附近 |
| **消化区收敛** | 新记忆在 K 个 MU 内被整理完毕，第二次穿过消化区时**原样通过** | 对比两次穿过的字节数，第二次应无变化 |
| **三档分布** | 条目位置呈"右端一小撮 / 0 附近一簇 / 左端一条长尾" | 对 `p` 做直方图，应只有一个峰且在 0 附近 |

**这些判据里没有一条用墙钟。** 这是这个设计成立与否的试金石。

其中"时间只向前"最容易被实现成错：如果召回的增加量没有上限，或没有无条件左行，一条被极频繁使用的记忆会**永远停在右端不回来**，那它既不在工作集里，也没被整理完——系统会出现一个只进不出的洞。

## 5. 与当前实现的距离（诚实清单）

现在已经有的：

- `memory_usage`（`inject_count`、`read_count`、`last_injected_at`、`last_read_at`）→ 是 `use` 的原料；
- `memory.importance`、`pinned`、`kind` → 压缩时的保护等级；
- `memory_edge`、去重（`possibleDuplicates`）→ 是"归纳/合并"的原料；
- `memory_head` / `revision` → 压缩可以写成**新 revision**，历史不丢；
- 记忆单位需要的计数器**不必新建**，可以从 `request_stat` + `write` 事件聚合。

还缺的（下面 §5.1 给出审计结果与实现顺序）：

1. **MU 计数器本身**（需要持久化，且要能解释"为什么涨了"）；
2. **位置 `p` 的存储**（每条记忆一个 `mu_position`，以及它的更新规则）；
3. **压缩执行器**：把一条记忆压成更短的形式（这一步要模型，属"记"的职责）；
4. **入口深度 `R`**：新记忆落在多远的右侧。R 大 = 消化慢、缓冲厚；R 小 = 新记忆很快到达工作集。
5. **`δ` 的下限**：见 §7.1。

第 4 条和第 5 条都**必须先测量再定，不能拍**——项目已经吃过一次"预算是拍的"的亏（`SLICE_BUDGET_BYTES = 1200` 至今没有收益测量）。

### 5.2 实现顺序（按依赖排列）

不需要模型、也不需要压缩执行器就能落地的五步：

1. **MU 计数器**：持久化，每次推进记录 `add` 与 `use` 两个分量（可解释性）；
2. **`p` 的推进规则**：每条记忆一个 `mu_position`，随 MU 左推、随召回右移；
3. **C1 → MU 阈值**：删除判据由"存在超过 30 天"改为"`p` 越过某阈值"，阈值由测量决定；
4. **C2 → `p`**：排序与 recency 项都改用 `p`，不再用 `updated_at`；
5. **C3 → MU 距离**：注入块写"距工作集 N 个记忆单位"，不写日历。

之后才是"压缩"本身：压缩执行器（要模型）、入口深度 `R`、`δ` 下限。


## 6. 一个必须写下来的反对意见

有人在读到这里时应该会问：**为什么不干脆全部保留，永不删除？**

答案是成本确实存在，但不是磁盘——磁盘很便宜。成本在**召回**：

- 注入切片只有 1200 字节，条目越多，单位字节里有用的比例越低（实测：600 条时精确率 7.5%）；
- 检索的候选窗口是有限的（`LIMIT 600`），条目越多，真正相关的那条越容易被挤出窗口；
- 整理本身**提高**可用性：把三条重复的合成一条，召回时一次命中就等于原来三次。

所以压缩不是"因为放不下才丢"，而是**"因为不整理会变差才整理"**。

## 7. 这个模型里有四个会咬人的地方

写下来不是反对，是它们必须在实现前定清楚，否则会以 bug 的形式重新出现。

### 7.1 不可逆深渊（最危险的一条）

如果逆幅 `δ(p)` 在 `p → −∞` 时趋于 0，而左行速度恒定，那么存在一个位置 `p*`，一旦越过，**无论召回多少次都回不来**。一条每年才用一次、但极其重要的规则（合规、审计口径），只要沉寂够久，就会被永久埋掉。

两条可能的解法，需二选一：

- **给 `δ` 一个下限 `δ_min`**：任何一次召回都有进展，只是非常慢；
- **让左行在远端也衰减**：最左端进入"黄昏区"，衰减极慢，永不彻底归零。

我倾向第一条：它保留了"左=值得遗忘"的语义，同时保证"仍被使用的东西不会死"。

### 7.2 反复穿过消化区 → 过度修剪

召回把记忆推向右，回家路上必须再次穿过消化区。于是**越常用的记忆被整理得越多次**，可能被压成一句没有细节的断言——恰好是最有价值的那些条目最先失去支撑细节。

所以修剪必须**收敛式而非轮次式**：每轮整理应以"是否还有可整理的东西"为停止条件，而不是"又过了一轮就再剪一刀"。已经干净的记忆第二次经过消化区应当**原样通过**。

### 7.3 "与同质记忆合并"需要一个定义

远端的主要机制是合并，而合并需要一个相似度判据。现有素材：`memory_edge`（图关系）、`embedding`（向量）、`entity`（实体）。但合并会产生**一条证据来自多个引文的条目**，而当前信任模型是"一条记忆 = 一个逐字引文"。合并后如何保持可溯源，需要单独设计。

### 7.4 "忙碌"会不会让记忆变老，这是设计还是副作用

你先前说"对话轮次很多但记忆没怎么增长时，旧记忆不该继续被遗忘"；这一版又说"所有记忆都有往左的趋势，因为往左是时间流动的方向"。**在 §0 的本体论下这两句不冲突**，因为"时间"只有一个所指：

> **MU 推进 = 时间流动 = 记忆变老。二者是同一件事，不是两件事。**
>
> 睡觉 → MU 不推进 → 时间没有流动 → 记忆一个 MU 都没变老。
> 忙碌 → MU 推进 → 时间真的流过了 → 记忆真的变老了。

所以"忙碌的一天会不会让陈旧记忆变老"这个问题本身要重述：**忙碌的一天里 MU 推进了多少**。若某天只发生少量召回而无新增，MU 推进很少，记忆几乎不变老；若那天涌入了大量新记忆，MU 推进很多，记忆确实变老——而那正是"这天发生了很多事"的正确表达。

于是原来的担心退化成**权重问题**：`w_use` 与 `w_add` 的相对大小，决定了"谈话量"与"知识增量"各自推动时间多快。这是可调的，不需要修改模型。
