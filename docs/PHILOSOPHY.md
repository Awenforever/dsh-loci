# dsh-loci 产品哲学

> 这份文件是指导思想，不是宣传材料。它的用途是：**当两个实现方案都说得通时，用这里的语句判定哪个是对的。**
>
> 编写原则：只写**已经被纠正到当下**的版本。凡是被推翻的说法，宁可删掉，不留"虽然…但是…"。

## 0. 一句话

**记忆 = 在需要的那一刻把对的那条端上来；而"哪条对"由模型判断，"多久算旧"由记忆单位度量。**

两件事都不能偷懒：判断交给模型，时间交给 MU。凡是把其中任一件交还给脚本或日历的设计，方向就是错的。

---

## 一、记忆 = 记 + 忆

「记忆」这个词本身就要求两件事同时成立：

- **记**：把值得留的东西准确地写下来
- **忆**：在需要的那一刻把对的那条端上来

| 只有一半 | 实际是什么 |
|---|---|
| 只有记 | 归档。写得再准，用的时候找不到，等于没记 |
| 只有忆 | 搜索引擎。检索再快，语料是空的或错的，等于没忆 |

**判定标准**：一项改动如果只改善「记」，必须说明它对「忆」的影响，反之亦然。任何一个方向没人管的版本，都不是在做记忆。

---

## 二、记忆必须由模型管理

类比大脑：清醒时主动记，睡眠时自动整理。两者都是有思考能力的过程，不是查表。

- **规则只能当便宜的预过滤**，用于明显的情形（"不要…"、"记住…"），不能充当判定层
- **分层处理（哪些留、留多久、放哪一层、要不要合并）必须交给模型**
- 模型在**契约之内自由发挥**：契约规定什么能写、写到哪、什么不能做；判断本身归模型

实测（`scripts/eval-memory.mjs` B 段）：规则分离器在真实语料上**召回 50%、精确 100%**——从不误报，但漏掉一半（`以后…`、`约定…是…`、`永远不要…` 全漏）。**安全但瞎。**

改成模型判定后的实测（真实模型，固定转录，连续多个版本复测）：

```
curator probe ok=true · caught=["deploy-first-canary","never-friday-release"] · missed=[] · keptNoise=[]
模型实际保留：Do not deploy on Fridays / Deploy via canary before full rollout
```

同一份语料，规则 50%，模型抓到全部。且它每次措辞都不同（`部署先走灰度` / `Deploy via canary` / `禁止在周五发版`）——**是在推理，不是在套模板。**

---

## 三、记忆管理者本身不得被记忆影响

**硬约束，不是优化项。**

记忆管理者（负责整理、晋升、合并、删除的那条链路）本身**不接受 dsh-loci 的任何注入**。所有记忆对它只是：可读的语料、可参考的上下文、可写入的对象。

**绝不能让管理者自己的系统提示被它正在管理的内容改变**，否则它会用被审查的内容去审查内容本身。

现状：已落地为**存储的事实** `injection_exempt`（按 session 记录），而不是依赖 `delegationDepth > 0` 这种副作用。段落与第二注入面（assist）都查这一条。

---

## 四、怎么「忆」与怎么「记」同等重要

这一点长期被本项目的实现忽略，评测把它暴露了出来。

**被否定的方案：静态索引**（`scripts/eval-memory.mjs` A 段，改前基线）

| 库规模 | 注入字节 | 命中该条的覆盖率 | 自然问法 | 改述问法 | 改述返回空 | 相关性 |
|---|---|---|---|---|---|---|
| 40 | 3278 | 87.5% | 100% | 0% | 92.5% | 1.0% |
| 600 | 3281 | 12.2% | 100% | 0% | 91.7% | 1.0% |

1. **注入字节恒定**——不管库多大、问题是什么，都注入同样 3.3 KB
2. **覆盖率崩塌**——库越大，真正需要的那条越不可能在里面（87.5% → 12.2%）
3. **改述必失败**——同一件事换个说法，92% 直接返回 0 条

结论：**静态索引不是「忆」，是「永远显示第一页」。**

## 五、忆的形态：小核心 + 当轮切片 + 可查指针 + 换词重查

- **恒在小核心**：跨对话都成立的规则与偏好，有硬上限（当前 500 B / 最多 6 条），只收 `kind=rule` 或 pinned
- **当轮切片**：按当前问题检索出相关的几条（当前 1200 B / 最多 8 条），严格层用连续 3 字符匹配，不中才用宽松层
- **可查指针**：一行「还有 N 条在作用域内，可用 `loci_search` 查」——让模型知道自己没看到什么。**没有这一行，切片看起来就是全部。**
- **模型换词重查**：切片没命中时，请模型把问题改写成另外几种说法再查一次

### 5.1 一个必须记住的排序事实（曾导致三个版本的白费）

`systemPrompt.assemble` **在 `preStep` 内部执行**，此时本轮的用户消息**还在 agent 的 inbox 里**（已 claim、未写入 session log）。

推论链：

1. 段**看不到本轮问题**；
2. 由 `session/event` 喂的追踪器**也看不到**（事件尚未触发）；
3. `capture` 的缓冲同理；
4. **唯一能拿到本轮问题的面是 `agent/pre-step` 的 `decision.messages`**——它是异步的，因此正好也能等模型。

所以架构是：**段只渲染不依赖问题的内容**（规则、计数指针、待审提示），**与问题相关的一切由 pre-step 组装并作为独立消息注入**。

这条曾经被写错过：段曾经按"上一轮"的消息检索，换话题的回合会被喂旧话题的记忆，而**旧的 query 恰好命中时，外观与命中完全一样**——救援只在"没找到"时触发，所以永远发现不了。

### 5.2 换词不是万灵药

改述问法在 600 条库上，词法切片能召回 **60.1%**，剩下约 40% 无论怎么调准入阈值都救不回来（`atlas 要发新版本` 与 `atlas 服务上线先走灰度` 只共享一个 token）。

用 **oracle**（喂正确答案）测上限：被错过的那些问题，**100% 都能被一次正确的改写救回**（76/76、115/115）。这解决了设计问题——改写原则上充分，剩下只是真实模型离 oracle 有多近。

## 六、记的形态：规则预过滤 + 模型判定 + 引文接地

```
转录 → 规则预过滤（便宜、宽松、宁多勿漏）→ 模型判定 → 引文闸门 → 落库
```

- **预过滤只做一件事**：把明显不可能含持久陈述的句子剔掉，减少模型调用。它**不做判定**。
- **判定归模型**：留下几条、是什么 kind、放在哪个 scope。
- **信任来自接地，不来自点击**：每条必须带一段**逐字出现在用户消息里**的 `evidence.quote`。闸门不过 → `candidate`；过了 → `verified`。
- **边界决定审批**：会话自身的话对它自己为真，故立即 `verified`；提升到工作区级会**重新打开闸门**。
- **指令形状的文本在任何 scope 都保持 `disputed`**，段永远是 `interpolate:false`。

实测（截至 4.14.0）：curator 在真实会话中产出 **9 条 `verified`**，全部通过引文闸门，无一条经过人工审批。

## 七、记忆单位是唯一的时间

**这是本体论，不是偏好。**

> 在 dsh-loci 的空间里，没有「时间」这个独立概念。**记忆单位的流动就是一切行为的标尺。**
>
> 说「流动」＝ MU 变了；说「更早／更旧／过期／该忘了」＝ `p` 更靠左。

因为 DSH 只在工作时才"活着"：用户睡一晚，对 DSH 而言**什么都没发生**。用墙钟度量"早期"，会让所有记忆在同龄化的 8 小时里一起变老，而其间零召回、零新增。

### 7.1 三条硬约束

| | 约束 | 违反的例子 |
|---|---|---|
| **C1** | 记忆不能因日历失效 | `working` 7 天过期、`candidate` 30 天关闭 |
| **C2** | "新旧"只能用 MU 距离表达 | `ORDER BY updated_at`、`exp(-age/30天)` |
| **C3** | 给模型看的年龄必须是 MU | 注入块渲染 `as of 2026-11-16` |

**5.0.0 已消除这三处**（此前三条全违反）：

| | 约束 | 曾经的违反 | 现在 |
|---|---|---|---|
| **C1** | 记忆不能因日历失效 | `working` 7 天过期、`candidate` 30 天关闭 | 已删除。退役判据为 `p > muRetireAfter`，阈值默认 **0（关闭）**，等测量 |
| **C2** | "新旧"只能用 MU 距离表达 | `ORDER BY updated_at`、`exp(-age/30天)` | `score → reads → mu_touched`；search 的 recency 项为 `exp(-p / 50)` |
| **C3** | 给模型看的年龄必须是 MU | 注入块渲染 `as of 2026-11-16` | `3.2 MU ago` + 一行 `ages are in MU (units of work, not dates)` |

**成本要写清楚**：本版之后没有任何按时间自动消失的路径，库只增不减，直到压缩动力学落地。这是有意的取舍——**宁可再生，不要因为日历而误删**。`doctor` 与面板显示四带分布，`cold` 增长可见。

### 7.2 MU 的定义

```
MU 增量 = log(w_add × 新增记忆量 + w_use × 召回活动量 + 1)

新增 = 0 且 召回 = 0  →  MU 冻结
```

取对数是有意的：它给出"再发生一点，边际寿命消耗递减"。

### 7.3 坐标轴：0 是栖息地，最右端是入口

```
遗忘 ←—— −  ——← 0 ←—— 修剪 ——← + ←—— 新记忆在这里落下
   压缩/丢细节              去枝末/归纳      （log 尾部，边际）
```

**所有箭头朝左，那是时间的方向。** 一条记忆的一生就是向左走，外加召回时的向右逆行。

| 区域 | 状态 |
|---|---|
| 最右端 | **入口**。log 尾部，变化极慢——这是"吞下蓝鲸也不慌"的来源 |
| `+` 区 | **消化区**。越靠近 0 **修剪越深**：去重、合并、丢碎枝、若干条归纳成一条 |
| **`p = 0`** | **栖息地**。消化完成、结构干净。**绝大多数有用的记忆应在附近** |
| `−` 区近端 | **压缩频繁**，细节丢得快（此时冗余最多） |
| `−` 区远端 | 已无可再压，只剩**与同质记忆慢慢合并** |
| 最左端 | 遗忘 |

### 7.4 动力学：时间推左，召回拉右

- **向左是无条件的**：每个 MU 把每条记忆往左推一点。时间也许可以逆转，但不可抵抗。它保证终止性——没有记忆能被永久钉住。
- **召回是向右的逆行**，幅度同样是 log 形状：**0 两侧是头部（大幅），离 0 越远越接近尾部（微幅）**。

一条曲线形状给出三个性质：

1. **稍微老化 → 一次召回就救回**（0 附近逆幅大）
2. **老化太远 → 要救就贵**（尾部逆幅微）→ "用过一次"与"一直在用"的差距不会被偶然使用抹平
3. **召回会触发重新整理**：被推右的记忆要回 0，**必须再次穿过消化区**

### 7.5 0 附近的聚集是稳态，不是设定

- 召回够频繁 → 左右抵消 → **围绕 0 振荡**
- 召回低于阈值 → 左行胜出 → 滑进压缩区
- 从未召回 → 一路向左 → 合并、遗忘
- 新来的 → 右端排队消化

**三档分布，没有一条规则去指名谁该留下。** 这就是要的效果。

### 7.6 弹性属于"入口"，不属于"压缩"

不要把它想成固定容量的桶（满了挤掉最旧）。一次灌入 50 篇文档 → 它们全落在右端 → **旧记忆根本不在这一段**，所以完全不受冲击。

**不是空间有弹性，而是新记忆的着陆点在远处。** 入口深度 `R` 与消化时间决定"吞下蓝鲸后多久消化完"。

### 7.7 四个会咬人的地方

1. **不可逆深渊**：若逆幅在远端衰减到 0 而左行恒定，则存在 `p*`，一旦越过**无论召回多少次都回不来**。一条每年用一次但极重要的口径会被永久埋掉。倾向给 `δ` 一个下限。
2. **过度修剪**：常用记忆每次回家都过一遍修剪，可能被压成没有细节的断言——**恰好最有价值的先失去支撑**。修剪必须收敛式，干净的记忆第二次穿过应原样通过。
3. **合并缺定义**：远端靠合并，但合并会产生"一条证据来自多个引文"的条目，而当前信任模型是"一条记忆 = 一个逐字引文"。合并后如何可溯源需单独设计。
4. **"忙碌变老"不是副作用**：MU 推进 = 时间流动 = 记忆变老，三者是同一件事。睡觉不推进则不老；忙碌推进多少，取决于那天**发生了多少事**。剩下的只是 `w_use` 与 `w_add` 的相对权重。

## 八、判定规则（遇到取舍按顺序问）

1. 这个改动是在改善「记」还是「忆」？另一个方向会不会变差？
2. 这个判断能不能交给模型？能，就不该硬编码成规则。
3. 它会不会让管理者自己被管理的内容影响？会，就否决。
4. 它是否让人做本可以由模型做的选择？（逐条审核、手动指定作用域）
5. 它用的是**记忆单位**还是墙钟？用墙钟，方向就是错的。
6. 有没有用数字证明它更好？**没有数字的改进，最多只能算假设。**

## 九、工程诚实条款（血换来的）

这些不是道德要求，是**已经造成过真实损失**的教训。

1. **严禁虚报完成。** 失败就报失败，写清原因与下一步。
2. **发布 ≠ 生效。** 装上不等于在真实使用中被验证过。要拿到真实事件作为证据，否则只说"已安装，未见触发"。
3. **诊断要写在失败发生的那一行里面**，不是旁边。"记录失败了"与"记录在哪一行、以什么理由失败"相差五个版本。
4. **修管线之前，先验证观测点能否看到目标。** 在确认入口有数据之前改管线，等于蒙眼改管道。
5. **指标不动时，先怀疑指标，再怀疑改动。** 静态索引的相关性从 1.0% 只"升"到 2.0%，不是改动无效，是分母已触底；换成上界由架构决定的精确率后，真实差距是 **21.5 倍**。
6. **一个会删数据的工具，必须对账。** "它认为要删什么"与"它实际要删什么"不一致时必须中止。曾经因为过滤只加在报告上、没加在删除循环上，误删了全部 12 条。
7. **共享过滤器之前，确认两侧需求是否相同。** 同一个 `source.kind === 'user'` 过滤器，对"持久抽取"是对的（注入的提示词不是人说的话），对"检索/整理"是错的——它已经造成两次独立故障。
8. **UI 改动先截图再交付。** 用 `client.js` 里的真实样式表在 headless 浏览器里出图，并回报实测尺寸。
9. **配置改动要先说再改**，尤其是别人的 profile。
