# dsh-loci v4 架构

> 本文定的是**目标架构**，不是现有实现的描述。旧实现可以当起飞平台，但不是绳索：
> 数据层（revision / FTS / 审计 / 凭证）经过 20 多个版本验证，保留；**注入层与捕获层推倒重来**。

## 一、为什么必须重构

`scripts/eval-memory.mjs` 的基线（E87）：

| 库规模 | 注入字节 | 覆盖率 | 自然问法 top-1 | 改述 top-1 | 改述返回空 | 相关性 |
|---|---|---|---|---|---|---|
| 40 | 3278 | 87.5% | 100% | 0% | 92.5% | 1.0% |
| 200 | 3281 | 17.5% | 100% | 0% | 92.0% | 1.0% |
| 600 | 3281 | 12.2% | 100% | 0% | 91.7% | 1.0% |

三个结构性缺陷，都不是调参能救的：

1. **注入与问题无关**——字节数恒定，说明「忆」根本没发生，只有「显示第一页」
2. **准入过严**——要求两个连续共享 token，改述后只剩主题名，于是 92% 直接 0 条
3. **规则只能做预过滤**——召回 50%、精确 100%，安全但瞎

## 二、分层

```
        ┌─────────────────────────────────────────────┐
 提示词 │  recall/  ← 每轮组装：核心 + 当轮切片 + 指针 │
        └────────────────┬────────────────────────────┘
                         │ 检索
        ┌────────────────┴────────────────────────────┐
 数据   │  store/  ← revision / FTS / 审计 / 用量      │
        └────────────────┬────────────────────────────┘
                         │ 写入
        ┌────────────────┴────────────────────────────┐
 记录   │  record/  ← 预过滤(规则) + 判定(模型)        │
        └─────────────────────────────────────────────┘
                         │ 模型调用
        ┌────────────────┴────────────────────────────┐
 管理者 │  curator agent（独立会话，**永不被注入**）    │
        └─────────────────────────────────────────────┘
```

## 三、recall/：把「忆」做成按问题检索

**组装顺序**（每轮）：

| 段 | 内容 | 预算 | 来源 |
|---|---|---|---|
| 核心 | 跨对话恒成立的规则与偏好 | ≤ 500 B 硬上限 | `layer='durable'` 且 `kind='rule'`，按 pinned 优先 |
| 当轮切片 | 与**当前用户消息**相关的条目 | ≤ 1200 B | 检索 top-k |
| 指针 | 「还有 N 条可查」 | 固定一行 | 作用域内总数 − 已注入数 |

**关键约束**：任何一段超预算就截断，绝不超额。总预算 ≈ 1.8 KB，不到现状的六成。

**准入要自适应**（解决 92% 零命中）：

1. 严格档：两个连续共享 token（现状）
2. 严格档返回 0 条时，**退一档**：允许单 token 命中，按匹配质量排序
3. 仍为 0 条才算真的没有

这不是放宽标准，是**区分「没有」和「有但说法不同」**。现在把两者混为一谈。

**模型换词重查**留作后续：模型本来就有 `loci_search`，第一次为零时应自己换词。一节里写清这个提示。

## 四、record/：规则预过滤 + 模型判定

```
会话事件 ──► prefilter（规则，便宜，高精确）
                 │ 候选池（宁可多收）
                 ▼
             curator agent（模型，判定）
                 │ 契约约束下的 JSON
                 ▼
             store.write（带 layer / topic）
```

**预过滤只负责"这段可能值得记"**，不负责判定。规则漏掉的（`以后…`、`约定…是…`）由模型补——模型看的是整段对话，不是单句正则。

**触发时机**（对应"清醒"与"睡眠"）：

- **清醒**：模型在正常工作中主动调 `loci_write`（已有工具）
- **睡眠**：会话结束（`agent/disposed`）触发 curator 整理

**curator 契约**（写死，不由模型自由发挥）：

- 输入：会话转录 + 现有相关条目摘要
- 输出：严格 JSON `{ keep: [{layer, kind, title, body, evidenceQuote, topic?}], merge: [...], drop: [...] }`
- 禁止：改删非本次涉及条目、写入 `global` 层（除非明确标注）、输出自然语言
- 失败：整体丢弃，不部分应用

## 五、管理者隔离（硬约束）

`recall/` 在组装前检查：**若本会话是 curator 或声明为管理者，直接返回空段**。

现有实现靠 `delegationDepth > 0` 巧合成立——那是副作用。改成显式注册表：创建 curator 时登记 sessionId，注入层查表。漏了就是缺陷，不是运气问题。

## 六、验证门槛

重构后必须用**同一个** `scripts/eval-memory.mjs` 复测。

**门槛表的第一版写错了指标**：它要求「相关性 ≥ 15%」，而相关性 = 需要的那条的字节 ÷ 注入总字节。这个定义把「没找到」也算成 0 并一起平均，于是它同时度量了两件事（找得到吗 / 找得省吗），任何一件变好都说不清是哪件。改成两个独立指标：

| 指标 | 基线（静态索引） | 要求 | S1 实测 |
|---|---|---|---|
| 每轮字节 | 3281 | ≤ 1800 | **901–969** ✅ |
| 自然问法：需要的那条在段内 | 87.5% → 12.2%（随库下滑） | 不下降 | **100%**（三档恒定）✅ |
| 改述问法：需要的那条在段内 | 0% | ≥ 50% | **58.3–62.5%** ✅ |
| 改述问法：完全没找到 | 92% | ≤ 15% | **0%** ✅ |
| 改述问法：靠第二档救回 | — | 记录 | 91.7–92.5% |

**未达成、且词法层做不到的**：600 条时改述仍有约 42% 找不到。这不是调参问题——`atlas 要发新版本` 与 `atlas 服务上线先走灰度` 只共享一个 token，任何词法放宽都救不回来。要做到必须引入**语义向量通道**（配置已有 `vectorMode` / `vectorEndpoint`，代码路径待接）。因此：

- **S1 可以达到的**：成本降七成、自然问法不退化、改述从 0% 提到约六成、失败不再是沉默
- **S1 达不到的**：剩下的四成改述。这一项留给 S1b（语义通道），不当作 S1 的失败

## 七、分阶段

| 阶段 | 内容 | 可独立验证 |
|---|---|---|
| S1 | recall/：核心 + 切片 + 指针 + 自适应准入 | eval A 段数字 |
| S2 | 管理者隔离注册表 | 单元测试：curator 会话段为空 |
| S3 | record/：预过滤 + curator agent | eval B 段召回 |
| S4 | 层模型（conversation / durable）与免审注入 | 端到端：写入后下一轮可见 |
| S5 | 装入 desktop，作为实验性功能参与真实任务 | 真实会话观察 |

**S1 就可以单独发布并使用**——它不依赖后面任何一阶段，且直接改善成本与相关性。
