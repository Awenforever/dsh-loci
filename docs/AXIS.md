# 带符号轴：p 的定义、动力学与参数

> 实现文档。`docs/MEMORY-UNITS.md` §3 描述模型，本文把它变成可执行的公式与列。
>
> **起因**：5.3.x 的实现是 `p = max(0, muNow - mu_touched)` —— 非负、无入口、无左移。方向上与 §3 相反：
> 新记忆落在 0（栖息地）而不是 +R（入口），越老 p 越大（往右）而不是往左。同一个 `mu_touched` 列
> 被写入、注入、读取三种事件刷新，所以 p 分不清「刚记住」与「刚用过」。实测：从未被注入的 23 条平均
> p = 366.56，而其中最新那条 p = 1.61 —— 两个数字在同一类里，这个维度失去了区分力。

## 1. 定义

```
遗忘 ←———— − ————← 0 ←———— 修剪 ————← + ←———— 新记忆在这里落下 (+R)
   p → −∞          压缩区     栖息地      消化区            p = +R
```

`p` 是**带符号**的位置，单位 μ，取值 `(-∞, +R]`。

| 区域 | 范围 | 含义 |
|---|---|---|
| 入口 | `p > R·(1−ε)` | 新记忆落下处。log 尾部，移动极慢 |
| 消化区 | `0 < p < R` | 向左滑行；越靠近 0 修剪越深 |
| 栖息地 | `p ≈ 0` | 消化完成。**多数有用的记忆应在这里** |
| 压缩区 | `−R < p < 0` | 开始丢细节；越左丢得越少（已无可压） |
| 遗忘 | `p ≲ −R` | 只剩与同质记忆合并 |

**0 不是时间戳，是平衡点。** 0 附近是唯一"没有损失"的位置。

## 2. 动力学

三条规则，互不重叠：

### 2.1 写入：`p = +R`

新记忆**落在入口**，不在栖息地。它与"刚被用过"是两种不同的处境：
一个还没被验证过用处，另一个刚刚证明了用处。

### 2.2 时间：每个 μ 无条件左移 1

```
p(t) = p(t₀) − (μ(t) − μ(t₀))
```

**不碰它，它也会往左走。** 这保证终止性——没有任何记忆能被永久钉住。

实现上**不做逐 μ 写入**，用锚点懒惰求值：存 `p_base` 与 `mu_base`，

```
p_now = p_base − (muNow − mu_base)
```

读的时候算一次，写只在召回时发生。

### 2.3 召回：`p += δ(p)`

```
δ(p) = max(δ_min, δ_base · exp(−|p| / scale))
```

- **0 附近逆幅大**：稍微老化的记忆，一次召回就能救回
- **越远越小**：老化太远的，要救就贵
- **`δ_min` 是下限**：保证任何一次召回都有进展，不存在"越过某点就回不来"的深渊

召回包括**注入**与**读取**。写入不算召回——写入是"落下"，召回是"被需要"。

## 3. 参数：四个，全部未校准

| 参数 | 初值 | 含义 | 测量方法 |
|---|---|---|---|
| `R` | 100 μ | 入口深度。R 大 → 消化慢、缓冲厚；R 小 → 新记忆很快冲击工作集 | 见 §4.1 |
| `δ_base` | 10 μ | p=0 时一次召回的幅度 | 见 §4.2 |
| `scale` | 50 μ | δ 的衰减尺度 | 见 §4.2 |
| `δ_min` | 0.1 μ | 召回幅度下限 | 不需要测——它是安全性下限，只要 > 0 |

**这些不是测量值，是初值。** 项目已经为"把猜的数字当测量值"付过代价（`CORE_BUDGET_BYTES = 500`
是为防填充物设的上限，却悄悄决定了 core 能放几条）。所以它们在代码里、`doctor` 里、面板里
都标注为 `uncalibrated`，直到校准脚本给出区间。

## 4. 怎么定这四个参数

### 4.1 `R` 怎么定：从"猜一个数"到"两个可算的边界"

`R` 是**一条从不被再用的记忆，从落下降到栖息地需要流过多少 μ** —— 一个以工作量为单位的寿命。

μ 的驱动重做完之后（`docs/MU-DRIVER.md`），这个数第一次**可以算**，因为新写入推进多少 μ 是已知的：

```
一条全新记忆推进 log(2) ≈ 0.693 μ        （重复的几乎不推进）
```

于是 `R` 被两个边界夹住。

**下界：一次灌入不得冲击工作集。** 批量写入 N 条全新记忆会把整个库朝左推 `0.693N` μ。要让它不把老条目推过栖息地，`R` 必须显著大于这个量：

| 一次灌入 | 推进 | `R = 400` 时占比 |
|---|---|---|
| 10 条 | 6.9 μ | 2% |
| 50 条 | 34.7 μ | **9%** |
| 200 条 | 138.6 μ | 35% |

50 条文档的一次性灌入只推动 9%，工作集不受干扰 —— 这正是 `MEMORY-UNITS.md` §3.3 要求的行为。

**上界：不被使用的记忆应当在一个季节内消失，而不是在一年之后。** 按实测速率 **30 μ/工作日**：

| `R` | 到栖息地 | 到遗忘端 |
|---|---|---|
| 120 | 4.0 天 | 6.4 天 |
| **400** | **13.3 天** | **26.7 天** |
| 1200 | 40 天 | 80 天 |

`R = 120`（v10 的初值）太短：一条周一写下的规则，周五就已经滑到压缩区，而它下周大概率还有用。
`R = 1200` 太长：库会长期只进不出，`forgotten` 区永远是空的。

**取 `R = 400`**：约两周工作到栖息地、四周到遗忘端。这是一个能对着经验检验的句子 —— *"一条规则如果一个月没再被用到，它就该淡出了"*。

#### 4.1.1 这个值的诚实状态

- **不是测量**。上表用的是**实测速率 30 μ/天**与**算出来的单条写入成本**，但"两周/四周"这个寿命目标本身是**设计判断**。
- **库还太年轻**：现在只有 ~29 μ 的寿命。`R = 400` 意味着现阶段几乎没有条目能自然走到栖息地。这是真实情况，不是故障 —— 一个一天大的库本来就不该有"安顿下来的记忆"。存量条目的位置是从旧模型推断的，不是挣来的。
- **真正能校准它的实验只有一个**：让库跑满几百 μ，观察 `p` 靠近 0 的条目是否确实"多数有用"。在那之前它是**速率推算 + 设计判断**，不是测量值。

### 4.2 怎么测 `δ_base` 与 `scale`

判据是**"稍微老化的记忆一次召回能救回，老化太远的不能"**：

1. 取若干条 `p` 刚过 0 的条目（刚开始压缩）；
2. 各注入一次，看 `p` 是否回到 0 附近 → 定 `δ_base`；
3. 取若干条 `p` 在 `−R/4` 附近的条目，同样注入一次，看位移量 → 定 `scale`；
4. 两者的比值就是 `exp(−|p|/scale)` 的形状。

当前 `δ_base = 30`、`scale = 100`，按「救援深度 ≈ R 的 6%」定，即 **23 μ ≈ 18 小时重工作量**：一条记忆如果一天之内被用过，一次召回就救回；放了一周，就得用很多次。

**在数据量不足时不要调这两个值** —— 现在库里的样本还不足以支撑任何"测出来的 R"。


## 5. 与旧实现的关系

| 旧 | 新 |
|---|---|
| `p = max(0, muNow − mu_touched)`，非负 | `p ∈ (−∞, +R]`，带符号 |
| 写入 → `mu_touched = now` → p = 0（栖息地） | 写入 → `p = +R`（入口） |
| 不碰它，p 只增不减（往右） | 不碰它，p 只减不增（往左） |
| 召回 → `mu_touched = now` → p = 0 | 召回 → `p += δ(p)` |
| 三种事件写同一列 | 三种事件各自记录 |
| 无负区 | 负区是压缩区，是模型的主要工作区之一 |

## 6. 迁移

现有条目只有 `mu_touched`，没有锚点。**起始位置取决于它有没有被用过**，而旧 schema 恰好把这件事记在了
`inject_count` 里：

| 旧数据 | 读法 | 锚点 |
|---|---|---|
| `inject_count = 0` | 从入口落下后一直向左漂 | `p = R − 距离` |
| `inject_count ≥ 1` | 上次触碰时它就在栖息地，此后向左漂 | `p = −距离` |

其中「距离」= `muNow − mu_touched`；`mu_touched = 0` 是 v7 的"无历史"哨兵，按距离 0 处理（不许凭空造出
几千 μ 的漂移）。

**第一版只用了一条规则**（全部按入口算），真实库的结果是 **45 条里 35 条挤在入口**——包括一条被注入
**442 次**的规则。那等于把库中最熟的东西描述成"全新未消化"，正好把轴要表达的那个区分反过来了。
按 `inject_count` 分开后：入口 21 / 消化 3 / 栖息 6 / 压缩 15。

**迁移无法恢复的**：一次而已与用了上千次的差别。旧列只存最后一次触碰，旅程的形状丢了。
新动力学会在下次召回时重建它。

**回滚代价**（已在 `docs/PRODUCTION.md` §6.1 实测）：退 schema 会同时丢掉 `applies` 分类与位置锚点；
内容无损，判断有损。

## 7. 这次重做必须避免的失败

| 失败 | 症状 |
|---|---|
| 又拍一个 R | `doctor` 显示 `R = 100 (uncalibrated)` 却没有任何测量路径 |
| 左移被实现成逐 μ 写库 | 每次 recordInjection 都全表更新，库写放大 |
| `δ_min` 设成 0 | 深渊重新出现：沉寂够久的条目无论召回多少次都回不来 |
| 召回也刷新"写入时间" | 老问题重演：p 分不清刚记住与刚用过 |
| 只改数据不改展示 | 面板还画四带，轴已经是三段 |

## 8. 判据：重做成功的标志

1. **方向**：一条新写入的条目在若干 μ 之后，`p` 变小（往左），不是变大；
2. **入口**：新写入的条目 `p = R`，不是 0；
3. **召回**：注入一次后 `p` 增大，且 `p` 越靠近 0 增幅越大；
4. **无深渊**：任意负值处注入一次，`p` 至少增加 `δ_min`；
5. **区分力**：`p` 与「是否被注入过」不是同一个维度——从未被注入的条目应当**停在入口附近**，
   而不是散落在全轴（旧实现里它们 p 从 1.61 到 366.56 都有）。
